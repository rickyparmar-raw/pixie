PIXIE GUIDE SCREENSHOTS — FIX INSTRUCTIONS FOR NEXT AGENT

CONTEXT
-------
pixie (this repo, apps/pixie) is a Slack bot that walks people through step-by-step
guides (lib/guides.js -> GUIDES object). Some guide steps attach a screenshot from
public/screenshots/<guide>/<NN>.webp, rendered in Slack via buildGuideBlocks() in
lib/guides.js and served statically (no auth) from lib/web/serve.js at
/screenshots/<path>.

  public/screenshots/submit-project/       (01-05.webp)

This matches the user's complaint exactly: "the screenshots ... is the same pictures

ROOT CAUSE
----------
public/screenshots pages like shop/, account/, projects/ (apps/game/web/{shop,account,
projects}/index.html, driven by apps/game/web/pixl.js) are real static dashboard
pages, but they render nothing without a valid Pixl session JWT:
  - pixl.js reads a `?token=` query param (or localStorage `pixl_token`) and calls
    the real production API at https://server.pixl.rsvp with that token.
  - No token / invalid token -> 401 -> pixl.js shows the "gate" card (the exact
    thing baked into every one of these screenshots).
  - There IS a `?preview=1` flag that suppresses the gate card ONLY when hostname is
    localhost/127.0.0.1 (see pixl.js `localPreview`), but it does NOT fake any data —
    API calls still 401, so item lists/character data just spin forever empty. I
    tested this directly (served apps/game/web/ with `python3 -m http.server`,
    opened /shop/?preview=1 in Playwright) — you get real page chrome (sidebar nav,
    "THE PIXL SHOP" header, search bar, filter tabs) but the item grid never loads.
    That's a big improvement over the gate card but still not a finished screenshot.

Whoever captured the current screenshots ran a headless browser against these pages
with NO valid token, got the gate card every time, and (for a few files) pasted fake
overlay labels on top instead of catching that the underlying capture was broken.

THE FIX: GET A REAL TOKEN, THE SAFE WAY
-----------------------------------------
apps/server has a purpose-built demo-login route for exactly this kind of situation —
DO NOT hand-rig a JWT yourself, use this instead:

  apps/server/src/routes/auth.ts, `GET /auth/demo?name=<name>`
  - Gated behind `ALLOW_DEMO_LOGIN=true` (env var, default unset/false).
  - Looks up or creates a `users` row with oauth_provider="demo",
    oauth_id=`demo_<slug of name>`, seeds an empty `player_state` row on first
    creation.
  - Returns `{ token, name }` — `token` is a real 30-day session JWT
    (issueSessionToken({ userId, displayName }) from apps/server/src/auth/session.ts),
    valid against the real production API, because it's signed with the real
    JWT_SECRET and the user row lives in the real Supabase DB the production API
    reads from.

Steps:
  1. Get apps/server's real .env (SUPABASE_URL, SUPABASE_SERVICE_KEY, JWT_SECRET —
     same values production uses). If you don't already have it, ask Ricky/Gabin/
     Ridit for it, or locate an existing local copy. Do NOT invent placeholder
     Supabase creds — the demo user needs to land in the SAME database that
     server.pixl.rsvp reads from, or the token will look valid (signature checks
     out) but the user row won't exist / API calls will fail.
  2. Copy that .env to apps/server/.env locally and add one line:
       ALLOW_DEMO_LOGIN=true
     Keep this LOCAL ONLY. Never set ALLOW_DEMO_LOGIN=true on the actual Railway
     "server" service / production env — that would let anyone on the internet mint
     a session for a fresh account with zero real auth. This flag is safe only
     because you're running the server on your own machine, unreachable from
     outside.
  3. `bun run --cwd apps/server dev` (or `bun run --cwd apps/server build && node
     dist/index.js`, check apps/server/package.json for the actual dev script name).
  4. `curl "http://localhost:3000/auth/demo?name=pixie-docs"` (adjust the port to
     whatever PORT your .env has). Save the returned `token`. Use a clearly-labeled
     name like `pixie-docs` or `pixie-screenshots` — NOT a real teammate's name —
     so this is obviously a documentation fixture account if anyone finds it later
     in the users table. This account can be reused for future guide-screenshot
     refreshes; don't delete it when you're done, just leave a one-line comment
     somewhere (this file is fine) noting it exists.
  5. You can now stop the local apps/server process if you want — the token is
     already minted and valid; you don't need the local server running to use it
     against the real https://pixl.hackclub.com pages.

CROP TIGHT, DON'T DUMP FULL PAGES
------------------------------------
Full 1600x900 mostly-empty-background screenshots are part of why the current ones
feel bad even before you get to the "same picture" problem. For each step:
  - Screenshot (or crop after the fact with sharp) just the relevant UI region —
    the shop item grid, the specific form field being described, the specific
    button being clicked — not the whole viewport.
  - create-hackpad's existing screenshots (public/screenshots/create-hackpad/*.webp)
    are the quality bar and the ONLY existing examples of the "focus highlight +
    pointer arrow" treatment mentioned in git log commit fbc6991. There is no
    leftover annotation script in the repo (checked — optimize-screenshots.js only
    does a plain sharp resize-to-900x900 + webp convert, no cropping/annotation
    logic). You'll need to build or hand-do the crop/highlight/arrow step yourself;
    use the create-hackpad images as the visual reference for style (open a couple
    of them to see the convention before you start).
  - Final format: match create-hackpad — .webp only, sharp .webp({quality:85}),
    resized so max dimension is reasonable (create-hackpad tops out under ~65KB/
    image). Delete the stale .png duplicates currently sitting alongside the .webp
    files in shop-purchase/, submit-project/, customize-character/ once you replace
    them — create-hackpad has no .png files, follow that convention.
  - File paths/names must stay exactly what lib/guides.js already references
    (e.g. "shop-purchase/01.webp") unless you also update the `screenshot:` field
    for that step in lib/guides.js — check GUIDES["shop-purchase"|"submit-project"|
    "customize-character"].steps[i].screenshot for the exact current mapping before
    you start, so you capture the right count of images in the right order.
